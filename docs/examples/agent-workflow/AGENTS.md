# Personal workflow

## Communication

- Lead with the answer or next action. Keep output concise, literal, and easy to scan.
- Number bounded multi-step actions; keep lists to five items or group them by priority.
- State concrete progress and blockers without routine narration, recaps, or pleasantries.
- When work needs a human action, end with one small next action. Give a concrete time estimate when useful and supported.
- Explain fully when asked; use headings so the explanation can be skimmed.
- Report errors as cause, evidence, and next diagnostic step. After three unsuccessful correction rounds, revisit the assumption instead of repeating the same fix.
- These preferences persist unless I say "normal mode" or "stop adhd mode".

## Work artifacts

- In work communications, introduce multiple details with a complete framing sentence and colon, followed by flat bullets. Return to a standalone sentence for the next point.
- In explicitly requested whiteboard mode, update the bound artifact before substantive chat output. Keep the chat to its link, a material change, or a blocker.
- For document review, open the exact artifact path. When session discovery is uncertain, use an explicit file rather than a "last response" command.
- Preserve useful session context. Put acceptance criteria, current decisions, and blockers in the canonical task artifact so handoffs and compaction do not depend on memory alone.

## Task boundaries

- Before autonomous implementation, use the `goal-contract` skill to bind the outcome, permissions, acceptance checks, and stopping condition. Reuse existing approved requirements instead of asking for them again.
- Mark completion only with evidence for every accepted requirement; report blocked or unrun checks explicitly.
- Distinguish implemented, verified, committed, pushed, and deployed. Ask before external writes or destructive actions unless already authorized.
- Keep unrelated discoveries in a backlog; complete the current scope before proposing more work.

## Conditional guidance

- Before preparing a Slack MCP write, load `slack-messages`. Slack-specific formatting does not apply to other tasks or Slack reads.
- Preserve explicitly chosen visual formats: use `system-atlas` for a maintained architecture atlas and `visual-explainer` for standalone HTML/slides. Load design-process guidance only when needed for that surface.
- Read long skill references only for the current branch of work. Give extraction workers the bounded extraction contract, not the full orchestration runbook.
