The system map

One repository, four capability profiles, three installation owners.

Chezmoi is the orchestrator. It selects a profile, renders files into $HOME, then runs ordered hooks. Homebrew or DNF owns native packages; mise owns portable runtimes and tools.

Where the truth lives

The active chezmoi root is declared by .chezmoiroot as v2/home. Package membership and versions live in .chezmoidata/packages.yaml. Authentication, tokens, databases, caches, and sessions remain local runtime state and are deliberately excluded.

Why the v2 prefix?

Migration history that outlived the migration.

v2 was a safe staging area for replacing the old macOS-oriented setup with a cross-platform, profile-driven system. It is no longer technically necessary.

Verdict

The prefix now communicates provenance, not architecture. Renaming v2/home to home would reduce nesting and eliminate a label that implies another live version exists.

The rename is worthwhile but not urgent. First fix scripts that hard-code v2/home; otherwise the cosmetic simplification can create bootstrap drift.

The important distinction is source versus rendered output.

Your understanding is correct: files ending in .tmpl under v2/home are source code. You edit them, and chezmoi renders them for the current profile.

Correction to the repository wording

Brewfile.tmpl and config.toml.tmpl are not generated files. They are hand-maintained renderers. Their outputs under ~/.config are generated.

For example, adding a cask belongs in packages.yaml. Changing how enterprise and desktop casks are selected belongs in Brewfile.tmpl. The current comment saying “Edit the inventory, not this file” means “do not put package facts here”; it should not imply that rendering logic is untouchable.

Three template behaviors

Ordinary configuration templates

dot_config/opencode/opencode.json.tmpl renders to ~/.config/opencode/opencode.json. Chezmoi strips .tmpl and decodes prefixes such as dot_ and private_.

Chezmoi's own configuration template

.chezmoi.toml.tmpl runs during initialization. It chooses and records the profile and pins the resolved source directory.

Lifecycle script templates

.chezmoiscripts/*.tmpl render into temporary shell scripts that chezmoi executes. run_once_ tracks first-time execution; run_onchange_ reruns when rendered content changes.

Why container CI fails

The container build is not usually exposing a Docker bug. It is repeatedly detecting that an upstream installer script changed while the repository's hard-coded checksum did not.

The recurring defect

curl -fsSL https://mise.run -o "$installer"
expected="3731df..."
[ "$actual" = "$expected" ] || exit 1
MISE_VERSION=v2026.8.6 sh "$installer"

MISE_VERSION pins what the script installs. It does not make https://mise.run immutable. When the vendor updates that moving endpoint, the fixed checksum correctly rejects it. The same pattern exists for https://terminal-browser.sh/install and https://plannotator.ai/install.sh.

Representative evidence: run 34525529820, the last successful window, and terminal-browser failure run 32290489873.

Fix correctness first

  1. Use immutable release URLs

    Download mise's versioned GitHub release installer, keep checksum verification, and tie URL, version, and digest together.

  2. Reject mutable URL plus fixed digest

    Add a validation rule so future vendor installers cannot quietly reintroduce this failure mode.

  3. Keep optional tools out of container bootstrap

    Terminal-browser is installed in containers but is not part of the smoke-test contract. Skip it unless the container explicitly tests it.

Then reduce exposure and runtime

The Dockerfile copies the whole repository before RUN ./setup, so nearly every change invalidates the expensive network layer. A successful run took about 3 minutes 19 seconds and restored 35 tree-sitter languages. Use BuildKit's GitHub Actions cache, separate stable dependency inputs from frequently changed files, and split deterministic rendering tests from a scheduled network integration test.

The mise-exec idea

The command was almost certainly mise exec, whose short alias is mise x.

Rio's pattern uses mise as a temporary tool launcher: install mise, ask it for a pinned chezmoi binary, then let chezmoi clone and initialize the public repository.

mise x chezmoi@2.72.0 -- \
  chezmoi init --apply --force \
  https://github.com/josephhaaga/dotfiles.git

The first chezmoi@2.72.0 is mise's tool declaration. Everything after -- is the command mise runs with that tool on PATH. Chezmoi accepts a full Git URL or GitHub shorthand and can use built-in Git when an external git executable is unavailable.

A simpler public bootstrap

sh -c "$(curl -fsLS https://get.chezmoi.io)" -- \
  -b "$HOME/.local/bin" \
  -t v2.72.0 \
  init --apply --force \
  https://github.com/josephhaaga/dotfiles.git

This installs chezmoi and lets it clone the repository into its standard source directory. The root-level .chezmoiroot tells it that managed source begins at v2/home. The profile template then records that resolved location, so later bare chezmoi commands work.

Important tradeoff

The shorter official command executes a remotely fetched installer script. The current setup verifies the installer script itself before running it. Simplification changes the trust sequence unless the one-liner uses an immutable, pre-verified installer.

A smaller, steadier system

Ordered by impact and risk, not by visual neatness.

Keep the four profiles and the package inventory. They solve real cross-platform problems. Simplify the edges around them.

  1. Fix immutable downloads now

    Version installer URLs, retain checksums, and make validation reject moving endpoints paired with frozen hashes. This addresses almost every recent container failure.

  2. Split render validation from network installation

    Run profile rendering and syntax checks on every push. Run the full internet-dependent container bootstrap on changes to bootstrap inputs, on a schedule, or as a non-blocking canary.

  3. Choose one bootstrap owner

    Prefer direct remote chezmoi initialization. Let chezmoi acquire the repository and let the repository install mise, rather than installing mise solely to acquire chezmoi.

  4. Derive the source root once

    setup and validate.sh both hard-code v2/home. Read .chezmoiroot instead so a future rename cannot break one path but not another.

  5. Retire the migration label

    After source derivation is centralized, rename v2/home to home and update the documentation. This is clarity work, not a reliability fix.

Documentation fix worth making

Change the contributor rule from “do not edit the generated Brewfile and mise config” to:

Proposed wording

Package names and versions belong in .chezmoidata/packages.yaml. Edit Brewfile.tmpl and config.toml.tmpl only to change rendering logic or static settings. Never edit their deployed outputs under ~/.config.
